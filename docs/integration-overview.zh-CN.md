# KNOT 接入体系总览

先确定两个角色：**模型发布方**定义商品的选择、约束、流程、价格和视觉规则；**应用接入方**根据用户动作调用服务、保存状态、展示结果。同一个团队可以兼任，但模型定义和用户配置是不同的数据。

## 一次配置如何流动

```text
模型作者：Product JSON → 发布模型及编译 digest → 服务启动加载
                                                   ↓
应用：Initial → 保存 State → 用户操作 → Apply(State, Event)
                    ↑                    ↓
                    └── 保存完整新 State / 渲染 Snapshot
                                         ↓
                               Quote(State) → 整机报价

恢复存档：Evaluate(State) → Snapshot → Quote(State)
```

Product 定义可能性；State 记录这个用户已选什么；Event 表示一次修改。Snapshot 是根据模型和答案计算出的当前流程、合法性、价格明细及视觉属性。Quote 单独计算“保留已有选择后，合法完整商品的价格范围”，避免把尚未选完的累计小计显示成整机价格。

## 哪部分由谁负责

| KNOT 负责 | 应用/部署方负责 |
|---|---|
| 编译和校验商品规则 | 作者界面、模型审核、发布和版本保留 |
| 校验答案、决定路径、清理失效答案 | 用户鉴权、会话身份、数据库 CAS/事务 |
| 计算价格、完整配置报价和候选整机价 | 金额展示、税费/库存/订单等未建模业务 |
| 输出视觉目标、资产 ID、颜色和可见性 | SVG/图片/三维资源、资源加载、浏览器渲染 |
| gRPC 与部署配置 | 网络、证书、监控、扩缩容、支付 |

KNOT 无服务端会话，不维护用户数据库。两次携带同一旧 State 的 Apply 都可能成功，应用必须防止保存时互相覆盖。报价不等于预留库存、生成订单或授权支付。

## 模型和服务的交付物

- **Docker 镜像**：服务程序，不内置你的商品，不要求调用方安装 Rust 或 KNOT 原生库。
- **Product JSON**：由部署方挂载；目录只放商品模型，启动时统一编译。
- **modelDigest**：模型编译身份，由发布方提供；不是文件 hash，也不是 productVersion 的别名。
- **proto / JSON Schema**：网络信封及其中 JSON 的契约。客户端可从 proto 生成代码，或使用已有示例。
- **协议/示例压缩包**：便于下载的集合，不是服务调用的强制依赖；前端也是可选的。

仅消费已有服务时，向运营方取得 endpoint、TLS 身份、proto 和模型 digest 即可。自己定义商品时，还要走 DSL 校验、模型编译和版本发布流程。目前镜像没有模型管理 API 或 manifest 子命令；发布方生成 digest 的工具及其边界见[模型身份](grpc/clients.zh-CN.md#模型身份)。

## 最容易混淆的五件事

1. 未回答、明确空多选、跳过，是三种不同状态；可选题不自动跳过。
2. 修改上游答案可能清除下游选择；必须保存返回的完整 State，不能只合并这次点击。
3. snapshot 的 estimated 小计与 Quote 的完整商品 range 不同；候选价是整机价，不是固定附加费。
4. 返回上一题只是选择 Quote 的 focus，不应修改答案或 revision。
5. gRPC OK 只说明收到业务信封，还要检查 result/quote 与 error 的 oneof 分支；失败不能覆盖状态。

建议先读 DSL 的完整小模型，再启动未修改的音箱，运行一个语言客户端的 20 次调用教程，最后修改自己的模型。这样可以分别定位模型错误、网络问题和应用状态处理问题。
